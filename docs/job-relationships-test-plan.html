A A back-dated assignment reaches every month (844)

Each set is a complete snapshot from its effective date — that is why creating one carries the previous set's items forward. A back-dated addition wrote to the set it created and to the active set, and to nothing in between.

A1 The reported sequence
Do

Add PM01 effective 01 Jul, then PM02 effective 01 Sep, then go back and add PM03 effective 01 Jun.

Expect: PM03 appears in the June set, the July set and September.
Before 844 it appeared in June and September and was missing from July — a month it was in force for. Reproduced on PostgreSQL 16 against the live definition; the four rows it produced matched Dev row for row.
A2 No two sets overlap
Do

With sets at 01 Jul and 01 Sep, add something effective 20 Jun. Read the new set's end date.

Expect: 30 Jun — the day before the next set starts.
It used to be bounded by the active set, giving 20 Jun – 31 Aug against an existing 01 Jul – 31 Aug. Two sets then claimed July and August, and "which set is in force on 15 July" had two answers. Nothing objected: the only index on the table enforces one open active set. ejrs_no_overlap now makes it impossible, and 844 aborts rather than installing a constraint the data contradicts.
A3 The walk stops where somebody else holds the slot
Do

September already has PM03 = someone else. Back-date PM03 = a different manager to 01 Jun.

Expect: June and July take the back-dated manager; September keeps its own.
An assignment continues until something says otherwise, and a set filling the slot with a different manager is something saying otherwise. A set already holding the same code with the same manager is walked past instead: carried-forward and deliberately-entered are indistinguishable in the data, and here they mean the same thing.
A4 And at a removal
Do

Remove PM03 effective 01 Sep, then back-date PM03 to 01 Jun.

Expect: June and July hold it; September stays ended. The removal is not undone.
A5 Re-picking a date that already has a set
Do

From the history panel, edit a closed set using its own effective date.

Expect: the set is edited in place. No new set, no error.
Pre-existing and found only by testing for it: the covering-set lookup used effective_from <= p_effective_from, matched the set starting on that very date, and truncated it to the day before its own start — 01 Mar – 31 May became 01 Mar – 28 Feb. The user saw chk_ejrs_effective_order by name. The unmodified 835 function does it too.
A6 Removals are not walked forward
Do

Nothing to click — read 844's header.

Expect: a retroactive removal still touches only the active set.
An add can be walked past an identical row because both readings mean the same thing. A remove cannot: a later row naming the same manager might be the assignment continuing (should end) or somebody re-entering it on purpose (must not), and ending it on a guess silently deletes a real assignment. Named, not forgotten.

B The mirror helper nobody created (845)

Two functions called sync_job_relationship_mirrors. It did not exist. Neither caught the failure.

B1 An approved change no longer rolls back
Do

Submit a job relationship change through workflow and approve it, dated today or earlier.

Expect: it applies.
Before 845 it raised function sync_job_relationship_mirrors(uuid, uuid) does not exist and rolled the whole approval back. Since June. Nobody noticed because the direct HR edit goes through a different function that mirrors inline — so the path everyone used worked, and the path nobody used was broken.
B2 461 could never have worked
Do

Nothing to click. Read 461's body: MAX(CASE WHEN relationship_code = 'PM01' THEN manager_employee_id END).

Expect: there is no max(uuid) aggregate in PostgreSQL.
So that text creates cleanly — CREATE FUNCTION does not resolve names inside a plpgsql body — and raises on first call. Restoring 461 verbatim would have restored the outage under a different message, and a database where 461 did apply has the same outage. Found because 845's verification calls the function instead of asserting it exists.
B3 An assignment ending in the future is still mirrored
Do

Give someone a relationship carrying a removal date in 2027 and check the mirror column.

Expect: the manager is still named. One ended on or before today is not.
The comparison is against CURRENT_DATE, not the blunt removed_on IS NULL that 835 uses inline. Blanking it early would tell the org chart somebody's manager changed before they did. 835's version is safe where it sits — it only meets the active set at the moment of a change — but it is not the general rule.

C The screen reads what the database records (846)

The report that started all of this: delimit an assignment, and nothing appears to happen. The database was right the whole time.

C1 A delimit is visible
Do

End a project assignment on a past date. Open Job Relationships.

Expect: that manager's slot is gone from the current panel.
removed_on appeared in zero client files and in exactly one migration besides the one that added it. Both RPCs this screen calls were last written by migration 360 — five months before 835 added the column. Meanwhile the mirror column was correct, so the database held two answers to "who is her PM03", and which you got depended on which reader you asked.
C2 And history stays honest about the months before
Do

Click back to a set that ended before the removal date.

Expect: the manager is still listed there.
removed_on is the first date the assignment is no longer valid within its set. An item ended 01 Sep was valid for every day of a 01 Jul – 31 Aug set. The blunt removed_on IS NULL hides it from July too, and July then says she had no PM03 during a month she did — the same defect as C1, arriving from the other side. So: current compares against today, history against each set's own start.
C3 A post-dated change does not take effect early
Do

Set a job relationship with an effective date months ahead. Look at the current panel today.

Expect: today's managers, not the future ones.
Live before 846 and reachable without any trigger: the reader picked its set by is_active = true AND effective_to = '9999-12-31' — "the open-ended set", not "the set in force today". Measured on 22 Sep with a set dated 01 Mar 2027, it returned the March set. Nothing prevents post-dating: 456 validates against the hire date, not the future.
C4 Edit no longer resurrects the dead
Do

On a set holding an ended relationship, press Edit, change nothing, save. Re-read the set.

Expect: the ended relationship is still there, still ended.
The edit path deleted every item and re-inserted from a payload that has never heard of removed_on, so one Edit wiped every removal marker on the set — and because history returned removed items as live, the form resubmitted them and they came back alive with nothing recording they had ever ended.
C5 …but a new manager in that slot starts live
Do

Edit the same set and assign a different person to the ended slot.

Expect: they are live, not pre-ended, and the mirror names them.
Markers are carried across the rebuild only where the manager is unchanged. A different manager is a new assignment and the old end date says nothing about it; inheriting it would mark somebody as gone before they started.
C6 History agrees with the table above it
Do

With a post-dated set present — say one beginning 01 Oct while today is 22 Sep — open History.

Expect: the Current pill on the period containing today; the 01 Oct period marked Scheduled and headed From 01 Oct 2026; the panel opens on the period in force, not on the scheduled one.
846 replaced is_active = true AND effective_to = '9999-12-31' in the server reader and left the identical test in the client, in two places. Reeshethaa's profile showed 01 Oct 2026 — Present · Current nine days before it started, with the period actually in force sitting below it unlabelled — while the table above, which 846 taught to select by date, showed the right thing. One fact, two readers, two answers.
C7 And with nothing post-dated, nothing changes
Do

An ordinary employee whose latest set is open-ended and already started.

Expect: that set is Current and the panel opens on it, exactly as before. No Scheduled pill anywhere.
The flag test and the date test give the same answer whenever nothing is dated ahead, which is why this went three months without being noticed.

D The approved path writes the same timeline (847)

Two functions write job relationship sets. Only one got 844's fix.

D1 A back-dated approval reaches later sets
Do

Repeat A1, but submit the back-dated change through workflow and approve it.

Expect: identical to A1 — June, July and September.
The approved path has its own case logic and never got the forward walk, so the bug Vj reported was still live on that route after 844 fixed the direct edit. Two writers, one job, different rules.
D2 An approved correction keeps its removal markers
Do

Approve a correction on a set that holds an ended relationship.

Expect: the ended relationship survives, still ended. Same as C4, other path.
Urgent because 845 unbroke this path. Until then it raised on the missing mirror helper, and a failed approval writes nothing — the outage was accidentally protecting the data.

E A future-dated end actually ends (848)

Vj chose: a future-dated end records nothing when you set it, and a job applies it on the day. Before 848 there was no job — and the one written for this in June was never scheduled and could not have run.

E1 Nothing happens before the day
Do

End a project assignment on a future date. Check Job Relationships.

Expect: unchanged — the manager is still there.
E2 And it happens on the day
Do

select apply_due_project_jr_ends('<the day after the end date>'::date);

Expect: due 1, released 1, and the slot carries that date as its end.
Pass a date to test it without waiting. The scheduled run passes none and gets CURRENT_DATE.
E3 Two projects, one manager — the slot is retained
Do

Same manager on two projects, employee on both, one ending and one continuing. Run the job past the first end date.

Expect: due 1, released 0, retained 1. The relationship survives.
The job calls the same sync_project_jr_on_remove the same-day path calls, so the shared-manager guard is not reimplemented. If it is right there it is right here, because it is there.
E4 …and released when the last one ends
Do

Run the job past the second project's end date too.

Expect: released.
E5 A missed night catches up
Do

Run the job weeks after a boundary fell due.

Expect: still applied. Run it again: due 0.
It asks which ended assignments still hold a live slot — a question about the present — not what changed yesterday. A job whose correctness depends on having run every day since is a job nobody can verify; this one is verified by running it.
E6 It is actually scheduled
Do

select jobname, schedule from cron.job where jobname = 'job-relationship-due-ends';

Expect: one row, 40 1 * * *.
461 wrote a nightly sync for this and its comment claims it was "added to nightly cron". cron.job held two entries, neither of them it. Written in June, never scheduled, and carrying the same unrunnable max(uuid). Three months, no signal. Check the row, not the intention.

F A removal is mentioned on the day it happens (852)

Shipped as 852. 849 reached Dev carrying an earlier draft of itself, and 850 answered a broader reading of the request — a period of its own on the last valid day. Neither file can be edited once recorded, so the rule below lands in 852, which also takes 850’s record-day split back out.

The rule is one line: show a removed item iff removed_on = effective_from. The period that begins on the day of the change carries the mention. The period before shows the manager normally — she held the role through all of it. No period after mentions her at all.

F1 The mention is on the day of the change
Do

Vijaya: PM01 Iqraa removed effective 01 Aug. Open History and select the 01 Aug period.

Expect: the continuing managers, then a dashed rule, ENDED, and PM01 Iqraa Shaikh struck through with Ended 31 Jul 2026.
Before this, nothing anywhere said the assignment ended — the slot simply emptied. 844 stamped the marker on the set being closed, which is a past record, and 846’s filter was the only reason it was ever visible at all.
F2 The period before it is untouched
Do

Same history, select 01 Jul – 31 Jul.

Expect: both managers listed normally. No strike, no ENDED group.
She was the PM01 every day of July. A removal dated 01 Aug says nothing about July, and striking her there would be a lie about the past. This is the case that caught the first attempt: hiding the closing-set marker also hid her, so the writer had to stop putting it there at all.
F3 And no period after it mentions her
Do

Select the 01 Oct period, and any later one.

Expect: no PM01 row at all — not struck, not greyed. Absent.
Carry-forward skips removed codes, so nothing later holds the row; and even if one did, removed_on < effective_from fails the equals test. That is the leak 849’s first draft let through, where a removal dated 01 Jul appeared on a period beginning 01 Sep.
F4 Both shapes of removal give the same picture
Do

Once where a period already begins on the removal date, once where none does.

Expect: identical — clean period, then the period beginning that day carrying the strike, then nothing.
844 writes these two differently (in place, or by closing and opening). The reader cannot see the difference and neither should you.
F5 The date shown is the one that was typed
Do

Read the badge.

Expect: Ended 31 Jul 2026 — the last day she held it, not 01 Aug.
removed_on is the first day it was not valid: right to store, wrong to print. History returns ended_on = removed_on - 1 so no reader does date arithmetic.
F6 Replacing a manager is not a removal
Do

Change who holds a slot. Then, separately, remove and re-assign the same slot in one action.

Expect: both read as a plain handover — new period, new person, no strike.
A slot whose occupant changed did not end. The ended row is written before the assignment loop so that a remove-and-reassign in one action finishes as an assignment; order decides it.
F7 A slot filled again later
Do

Remove PM01, then assign somebody to PM01 a few weeks on.

Expect: the strike on the removal period only; the later period shows the new person, live.
F8 A future-dated end still shows nothing
Do

End an assignment on a date next month. Check today.

Expect: listed normally, no strike anywhere.
Vj’s decision in E: a future end takes effect on the day, applied by the 848 job. Until then it is a live assignment.
F9 Edit does not raise the dead
Do

History → the period carrying the strike → Edit. Look at that role’s picker. Then Save without touching anything.

Expect: the picker is empty; after Save the row is still struck, same date.
Check this every time history’s payload changes. admin_update_job_relationship_set rebuilds the set from what the form submits; an ended item arriving pre-filled would be re-submitted as live and the assignment would come back with nothing recording it ever ended. 846 made the server carry markers across the rebuild; the client keeps them out of the form. Both halves are needed.
F10 844’s own behaviour is untouched
Do

Re-run A1–A6: the back-dated add reaching every later period, the same date picked twice, the overlap constraint.

Expect: all pass unchanged.
852 edits the removal path in three places and one filter. Everything else in that function is 844’s; the migration asserts the forward walk, the exact-date branch and 851’s provenance all survive, but only A1–A6 proves they still work.
F11 A manager hidden from a period he held it — repaired
Do

Harikrishnan A, period 01 Aug – 21 Sep, PM02 Mohammed Insaf.

Expect: PM02 listed normally for that period, and the period beginning 22 Sep carrying him struck with Ended 21 Sep 2026.
852 alone made this worse before 853 fixed it. His marker was on the period being closed, the shape 844 wrote; the equals rule hid that row, so the period showed no PM02 at all — for a manager he held every day of it. 852 stopped the writer creating these. It could not move one already written.
F12 A removal recorded two months after it happened — repaired
Do

Vijaya, PM01 Iqraa. Check the period beginning on the removal date, and the 01 Oct period.

Expect: the mention on the period that begins on the removal date; nothing on 01 Oct.
Her marker had been carried into a period beginning two months after the removal it recorded. 853 moves it to the day it names and deletes the row that never belonged there.
F13 An Edit cannot plant a marker on the wrong period
Do

Open a period in History, Edit, save. Then have an approved correction rewrite a set.

Expect: markers that name that period survive; one that names a different date is not restored — neither struck nor live.
This is how the two strays were made. admin_update (846) and 847’s correction branch both put saved markers back carrying their original date, with nothing checking it falls on the target’s start. Put a 01 Aug marker into a set beginning 01 Oct and you get Vijaya’s row.
F14 And nothing of an unknown shape was touched
Do

Read 853’s deploy log for LEFT ALONE notices.

Expect: none on Dev — the scan found only the two known shapes. Any that do appear are named in full and were not changed.
A marker strictly inside a period is neither a closing-set marker nor one carried forward, and no rule in 853 covers it. Inventing a reading for a row nobody can explain is how this thread started; the migration counts them and says so instead.
F15 A removal on an employee who has a scheduled change
Do

An employee with a period dated ahead — Vijaya’s shape. Remove a manager effective today.

Expect: the period beginning today carries the strike, the period before shows the manager normally, the scheduled period says nothing, and the live table drops them.
Silent before 854, and this is not the rare case it sounds like. 844 chooses its branch by comparing the removal date with the open-ended period’s start, not with today. Give an employee any scheduled future change and every removal dated before it — including one dated today — took the retroactive path, which created the right period and then wrote the record somewhere it could never be read.
F16 A genuinely back-dated removal, and it still takes effect
Do

Today, remove a manager with an effective date weeks in the past.

Expect: the period beginning on that date carries the strike; the period before it shows the manager normally; the live table no longer lists them.
The action leaves two rows: a hidden one on the current period, which is what actually ends the assignment, and a visible one on the day it happened. Same division of labour the other branches have had since 852. The hidden one is load-bearing — 853 will not delete a marker it cannot re-record for exactly this reason.

H A slot remembers which project put it there (851)

A PM slot now records the project that filled it. NULL means a human did, and automation never touches it — which is every row that existed before this migration, because nothing was backfilled. Changing a project's lead moves the slots that project owns and nothing else.

H1 Nothing you already have moves
Do

Before anything else. Pick an employee with PM slots that pre-date this deploy. Change the lead of a project they are on.

Expect: their slots are unchanged. Nothing this migration does can move a row created before it.
No backfill was the deliberate choice. A backfill would have had to guess which existing slots were project-derived — the guess the column exists to avoid — and a wrong guess overwrites an assignment somebody made on purpose. The behaviour below begins with memberships created after the deploy, so test it with fresh ones.
H2 The handover
Do

Create a project led by Suchitra, add a member, then change the lead to someone else.

Expect: two periods — … – yesterday holding Suchitra in the slot, today – Present holding the new lead in the same slot. No strike.
A replacement, not a removal plus an add: the slot never ended, its occupant changed, and a set boundary is exactly how that is recorded. 849's record day and strike are for things that ended.
H3 A hand-set slot survives the change
Do

As H2, but first assign someone to another slot by hand through the portlet. Then change the project's lead.

Expect: the project's slot moves; the hand-set slot is untouched, same person, no new boundary of its own.
The whole point of the column. Naming a manager for a slot — through the portlet, through the approval path, through a history Edit — clears ownership, because a human just made a decision about it.
H4 Shared manager: the slot is kept and re-homed
Do

Suchitra leads two projects; one employee is on both. Change the lead of one of them.

Expect: Suchitra stays in her slot, now owned by the project that still justifies it, and the incoming lead is placed in the next free slot, owned by the project that changed.
834's rule, applied to a change rather than an ending — the same case Vj raised for end dates. The assignment is still earned by the other project, so removing it would be wrong; but the new lead is genuinely new and needs a slot.
H5 Clearing the lead ends the assignment, with a record
Do

Set the project's manager to empty.

Expect: the period beginning today carries the old lead struck through with Ended <yesterday>, and no later period mentions them.
Nobody is taking over, so this is a removal and 852 records it the way it records every other removal. The two migrations meet here.
H6 The incoming lead is not listed twice
Do

An employee already has Iqraa as a manager through another project. Change a second project's lead to Iqraa.

Expect: the second project's slot ends, struck on the day. Iqraa appears once, in the slot she already held.
Two slots would claim she manages the person in two capacities, which is not what happened. One slot cannot record two owners — a known limit, written down in the migration header.
H7 Ending a membership after a handover releases the right slot
Do

H2's project, after the lead change. Now delimit the member's assignment.

Expect: the slot is released, on the right date, with 849's record day.
Before 851 this was broken and nobody would have seen it. sync_project_jr_on_remove looked up projects.manager_id — the current lead — and matched on the person, so after a handover it released the new lead's slot, or matched nothing and released none. It now asks the slot which project owns it.
H8 Ownership survives an unrelated edit
Do

Create a project-derived slot, then make an unrelated change through the portlet so a new set is created. Then change the project's lead.

Expect: the lead change still moves that slot.
Each set is a fresh snapshot and carry-forward rebuilds the rows. Without copying the column through every carry-forward, ownership would be correct until the next unrelated edit and then silently empty — and the failure would look exactly like "the feature does not work sometimes".
H9 Renaming a project changes nothing
Do

Edit a project's name, type, or budget — anything but the lead.

Expect: no new job-relationship sets for anybody, no boundaries, nothing.
The trigger is narrowed to UPDATE OF manager_id, 797's rule. The migration asserts it; this confirms it on real data.
H10 A failed sync does not roll back the project edit
Do

Not clickable. Read trg_projects_jr_on_lead_change, then check the Postgres log after a lead change.

Expect: the whole sync is wrapped; a failure leaves a WARNING and the lead change stands.
Both sync functions used to end EXCEPTION WHEN OTHERS THEN NULL. They now raise a WARNING. 845 sat unrunnable for three months behind exactly that silence, and was found only because something finally called it. A sync that cannot run must not also be quiet.
H11 And G3 is closed
Do

With a post-dated set present, add a member to a project.

Expect: the free-slot search consults the picture in force on the date the membership starts, not the post-dated one.
Both sync functions were rewritten here, and leaving the flag test inside a body being replaced would not have been a saving. This is the last of the four places 846 could not reach.

G Known and deliberate

Decided, written down, and not fixed. Each is here so it is met as a choice rather than found as a surprise.

G1 The job ends, it never adds
Do

Assignment ends 31 Aug; a new project with the same manager starts 01 Oct, booked in advance.

Expect: the slot is released on 01 Sep and nothing restores it in October.
September is correct — she is on none of his projects that month. October is not. sync_project_jr_on_add already ran when the membership was created, found the manager still in a slot, and returned; it will never run again. The job cannot safely add, because a slot can be set by hand as well as by a project and nothing on the row records which — re-adding every manager a project implies would undo deliberate removals. 851 added the provenance it was waiting for — source_project_id, so the job can now tell its own slots from a human’s. The adding half is written but not built: it still has to decide which project’s manager wins when two of them start the same month.
G2 Four readers still treat an ended relationship as live
Do

Nothing to click while Prowess is in testing.

Expect: the bulk export lists ended relationships; nobody is notified that one ended; the approver's "before" picture in both submit_change_request overloads shows them as current.
These produce wrong display, and nothing acts on that output yet. 846 and 847 covered the paths that write wrong data. Revisit before go-live.
G3 Only six of the codes have mirror columns
Do

Compare the mirror columns on employees with the slots the sync functions search.

Expect: columns for PM01–PM03 and OM01–OM03; slot-finding searches PM01–PM06.
A project whose manager lands in PM04 or PM05 cannot reach the mirror at all, so anything reading employees.pmNN_manager_id is blind to it. The mirror is a cached copy of a fact the item table already holds correctly — the same shape as the dead projects.project_type column 840 removed. Worth asking whether it should be a view rather than columns.
G4 A handover into the same slot records no ending
Do

Replace who holds a slot — either in one action, or as a removal followed by an assignment to the same slot on the same date.

Expect: no strike. The period before shows the outgoing manager, the period from that date shows the incoming one. In the two-step version the strike appears after the removal and is then overwritten by the assignment.
Decided, not overlooked. uq_ejri is unique on (set_id, relationship_code), so one period holds exactly one row per slot: it can say "Iqraa ended" or "Suchitra holds it", never both. Recording both would mean dropping that constraint for something like "one live row per slot per period" and teaching every reader that a slot can return two rows — get_current, history, the mirror sync, both project syncs, admin_update, 847's transition, and the portlet's slot lookups, each of which assumes one.
A slot whose occupant changed did not end; it changed hands, and the boundary says so. A genuine vacancy is still recorded — if the incoming manager takes a different slot, the outgoing one is struck as normal. Revisit only if the two-step path's disappearing strike causes real confusion; the cheaper fix then is to make it behave like the one-step path and never write the strike at all.

If something fails, the "why this matters" note on each case names the rule it is testing — start there. The migration headers for 844 to 854 carry the reasoning in full, and docs/job-relationships-design.md has the original model.

Known open items are section G, and they are open on purpose. G1 — the daily job releases relationships but never restores them — is the one most likely to be reported as a bug. 851 removed what was blocking it, so it is now a decision rather than an obstacle.

Method. Every migration here was reproduced on a real PostgreSQL 16 against the live function definitions read from Dev, not from the migration files: the files do not add up to what is running. Each was then re-run to prove idempotence. Four verification blocks failed during development because an assertion matched the migration's own prose rather than its code — if you write one, match a predicate, not a phrase.
