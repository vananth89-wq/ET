Do

On the day from A1, Add Attendance → same type → project A again → 1h → Save.

Expect: the save is refused. The unique index does its job.

§ The five notification checks — Q1 to Q5

Referenced throughout sections X and Y. All five are read-only — paste into the Supabase SQL editor and run one at a time. Q1 and Q2 read the configuration and can be run before anything is submitted; Q3 and Q4 read what a real run actually sent; Q5 is the one worth running even when nothing has changed. Also kept in the repo at docs/notification_checks.sql.

Q1 What wording does each event resolve to today?

Mirrors the order wf_queue_notification uses (mig 748): step first, then template, then the generic wf.* code. The step column is evaluated at step 1, which is where wf_submit creates the first task; a multi-step workflow resolves against whichever step is current when the event fires.

WITH tpl AS (
  SELECT DISTINCT wa.wf_template_id AS template_id
  FROM   workflow_assignments wa
  WHERE  wa.module_code = 'timesheet'
),
ev(event_code) AS (
  VALUES ('wf.task_assigned'), ('wf.completed'), ('wf.rejected'),
         ('wf.returned_to_previous_step'), ('wf.clarification_requested'),
         ('wf.clarification_submitted'), ('wf.withdrawn'),
         ('wf.sla_reminder'), ('wf.sla_escalation')
)
SELECT
  wt.code || ' v' || wt.version                       AS workflow,
  ev.event_code,
  CASE WHEN step_n.code IS NOT NULL THEN '1 · step'
       WHEN tmpl_n.code IS NOT NULL THEN '2 · template'
       ELSE                              '4 · system default'
  END                                                 AS resolved_at,
  COALESCE(step_n.code, tmpl_n.code, ev.event_code)   AS template_code,
  COALESCE(step_n.title_tmpl, tmpl_n.title_tmpl,
           '(generic workflow wording)')              AS subject_line
FROM       tpl
JOIN       workflow_templates wt ON wt.id = tpl.template_id
CROSS JOIN ev
LEFT JOIN  workflow_steps ws
       ON  ws.template_id = tpl.template_id
       AND ws.step_order  = 1
       AND ev.event_code  = 'wf.task_assigned'
LEFT JOIN  workflow_notification_templates step_n ON step_n.id = ws.notification_template_id
LEFT JOIN  workflow_template_notifications wtn
       ON  wtn.template_id = tpl.template_id
       AND wtn.event_code  = ev.event_code
LEFT JOIN  workflow_notification_templates tmpl_n ON tmpl_n.id = wtn.notification_template_id
ORDER BY   workflow, ev.event_code;
Q2 Which steps have their own notification bound?

Before binding anything in the UI this returns "(none)" for every step. After binding, the step you edited should name timesheet.hr_review — that is the dropdown proving it wrote.

SELECT
  wt.code || ' v' || wt.version                     AS workflow,
  ws.step_order,
  ws.name                                           AS step,
  COALESCE(n.code, '(none)')                        AS notification,
  COALESCE(n.title_tmpl, '—')                       AS subject_line
FROM       workflow_steps ws
JOIN       workflow_templates wt ON wt.id = ws.template_id
LEFT JOIN  workflow_notification_templates n ON n.id = ws.notification_template_id
WHERE      ws.template_id IN (SELECT wf_template_id FROM workflow_assignments
                              WHERE module_code = 'timesheet')
ORDER BY   workflow, ws.step_order;
Q3 What did the engine actually queue for timesheets?

template_code here is the code AFTER resolution, so it is the direct answer to "did my override win". status 'pending' that never turns 'sent' means the queue trigger or the Edge Function is the problem, not the wording.

SELECT
  q.created_at,
  q.template_code,
  q.status,
  q.error_message,
  e.name                                            AS sent_to,
  e.business_email,
  wi.metadata ->> 'period_label'                    AS period,
  wi.metadata ->> 'employee_name'                   AS timesheet_of
FROM       workflow_notification_queue q
JOIN       workflow_instances wi ON wi.id = q.instance_id
LEFT JOIN  profiles  p ON p.id = q.target_profile
LEFT JOIN  employees e ON e.id = p.employee_id
WHERE      wi.module_code = 'timesheet'

Q5 Does every placeholder used actually exist?

The failure this catches is silent at configuration time and embarrassing at delivery time: {{approver_name}} is not in the metadata submit_timesheet writes, so it renders as the literal characters {{approver_name}} in an email an approver reads. Compares the placeholders in every template bound to a timesheet workflow against the keys real timesheet instances carry.

'message' is expected to show as supplied-by-action: it is added to the payload by the clarification call, not by the instance metadata.

WITH bound AS (
  SELECT DISTINCT n.code,
         n.title_tmpl || ' ' || COALESCE(n.body_tmpl, '') AS txt
  FROM   workflow_template_notifications wtn
  JOIN   workflow_notification_templates n ON n.id = wtn.notification_template_id
  JOIN   workflow_assignments wa
         ON  wa.wf_template_id = wtn.template_id
         AND wa.module_code    = 'timesheet'
  UNION
  SELECT DISTINCT n.code,
         n.title_tmpl || ' ' || COALESCE(n.body_tmpl, '')
  FROM   workflow_steps ws
  JOIN   workflow_notification_templates n ON n.id = ws.notification_template_id
  JOIN   workflow_assignments wa
         ON  wa.wf_template_id = ws.template_id
         AND wa.module_code    = 'timesheet'
),
ph AS (
  SELECT code, (regexp_matches(txt, '\{\{\s*([a-zA-Z_]+)\s*\}\}', 'g'))[1] AS placeholder
  FROM   bound
),
mkeys AS (
  SELECT DISTINCT jsonb_object_keys(wi.metadata) AS k
  FROM   workflow_instances wi
  WHERE  wi.module_code = 'timesheet'
    AND  wi.metadata IS NOT NULL
)
SELECT DISTINCT
  ph.code                                           AS template_code,
  ph.placeholder,
  CASE
    WHEN ph.placeholder IN (SELECT k FROM mkeys) THEN 'ok'
    WHEN ph.placeholder = 'message'              THEN 'ok — supplied by the action'
    ELSE 'MISSING — renders as literal braces'
  END                                               AS status
FROM     ph
ORDER BY status DESC, template_code, placeholder;

AH Known and deliberate (780–788)

Three behaviours read as bugs without the context. Record them as observations, not failures.

The dropdown is an offer, not a rule. A direct API call can still write an entry against any active project. No enforcement trigger has been added: it is the one change that can stop somebody recording their week, so it waits behind a read-only audit of how much existing data it would refuse.
A project you have already booked to stays offered on dates inside its own window, even after your allocation ends. Deliberate — an entry that exists must be able to name its own project. Closing it needs enforcement with an exemption for existing rows.
An allocation may run past the end of its project, with no warning. Data hygiene rather than behaviour: the project window binds anyway, so the surplus grants nothing. A warning on My Projects is a candidate follow-up.

If something fails, the "why this matters" note on each case names the rule it is testing — start there. Rules are cross-referenced in the Timesheet Rules Guide, and the migration headers for 726 and 727 carry the reasoning in full.

Known open items going in: A2's wording; the PDF has never been generated in a real browser before M1. Delete still writes directly rather than through an RPC — and an RLS-filtered DELETE is not an error: it removes zero rows and reports success, so a refusal is indistinguishable from a deletion. That is how a missing timesheet.delete grant presented as a button that simply did nothing. Copy Day is no longer untested — it was exercised on 12 Aug and failed twice; both are section Q.

The working week is Sunday–Thursday. Prowess works Sun–Thu with Friday and Saturday off, and General (GEN) is configured that way on purpose. Expect Fri and Sat to render grey and a full August to plan at 176 hr, not 184. Noted here because it looks like a bug to anyone who assumes Mon–Fri — it was read as one on 12 Aug, off the back of an employee record that said Chennai, and the correct response to a schedule that looks wrong is to ask what week the company works before touching it.

The defect behind 734, 736 and 737. Migrations 729 and 730 changed save_timesheet_entry by patching the LIVE function body — pg_get_functiondef, string replace, EXECUTE — because the alternative was retyping a 200-line function to change one line in it. After that, no file anywhere held its real definition. Migration 733 then rebuilt it with CREATE OR REPLACE from 728's file, silently reverting both later rules; 734 restored one and asserted only that one; 736 restored the other. Three migrations to undo one rebuild. A CREATE OR REPLACE built from an older file is a revert of every in-place patch since, and it announces nothing. pg_get_functiondef is the only honest source for a function that has been patched in place. 736 PART 3 and 737's verification now list every rule each function must carry, with an instruction to extend the list — so the next rebuild fails its own deploy rather than reaching an employee.

A migration is frozen the moment it is pushed. 20260819753 was committed, pushed and applied to Dev; its contents were then edited and pushed again. Both runs went green and neither said anything. supabase db push keys on the migration VERSION, not on what the file says, so the second push skipped it and Dev kept the pre-edit row — while UAT and Prod, which had never run it, would have created the edited one. The same file, two databases. Migration replay stayed green throughout because it rebuilds from an empty shadow database where the current file does run: the two CI workflows were both telling the truth, about different things. Once a version number has been pushed, change it with a new migration, never by editing the file. 757 is that new migration; Y13 is the check.

Two wrong answers on 12–13 Aug came from reading a migration out of a stale local snapshot rather than out of the repo. 729 had since been revised — allows_future ungated from absence — and the snapshot still held the superseded draft, comments and all. A migration's header describes its intent ON THE DAY IT WAS WRITTEN; the database describes what is true now.

And a third, found while writing 738. A verification block died with malformed array literal instead of naming the rule that was missing. v_missing := v_missing || 'some text' on a text[] resolves to array || array, not array || element: Postgres casts the unknown literal and tries to parse the message AS an array, which fails because it has no braces. Cast it — || 'some text'::text. Migrations 734, 736 and 737 carry the pattern uncast; it has never fired there because every append sits on a failure path, so the bug is latent rather than harmless. Those blocks still abort the deploy, which is their job — they would simply report the wrong thing on the one occasion anyone needed them. They are left alone deliberately: rewriting an applied migration to improve an error message is a habit whose next instalment is rewriting one to change behaviour. 738's are cast, and 738's block has been proved to fire correctly by deliberately removing a rule from save_timesheet_entry and watching it name that rule.

The general shape of all three. Each was an assertion that was never run in its failing state. A guard nobody has watched fail is a guess about what it will say.

Why N exists at all. Every timesheet RLS policy asked user_can() for a module named timesheet. No such module existed — the permissions were filed under time_management — so every check returned false for everyone except the super-admin allowlist, which short-circuits before any of it runs. The product worked for four months because the only people using it could not be refused. Section N is written to be run as somebody ordinary, which is the only way that class of bug is visible at all.

Why P is nine cases for one error message. The reported symptom was a constraint name on screen. Underneath it were four distinct outcomes the day panel had no opinion about, a second unique index one level down that a naive fix would have tripped, a note being discarded on a path nobody had looked at, and a catch-all handing Postgres's own words to the browser. One visible failure, five things to prove.

Why J15 exists. It was added after the bug it describes reached the browser. The plan had a case for editing an entry and a case for deleting one, and both were written as tests of the DATABASE trigger — which worked perfectly. What failed was the screen re-reading the result, on two write paths out of four. When a rule is enforced in one place and displayed in another, a case has to name which of the two it is exercising, and cover every route to it.
