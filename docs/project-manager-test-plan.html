Project Manager Test Plan

A project lead is now derived from the project record, sees their own project's hours and nothing else, staffs their own team, and cannot strand somebody's time by moving a date. These are the checks that prove it on Dev.

Scope. Migrations 20260826780 through 20260826788, plus the My Projects and My Timesheet screens. Migrations 726–776 — the paste, holiday and workflow work — are covered by the separate docs/timesheet-test-plan.html and are not repeated here. Every case below has a corresponding sandbox assertion; this document is the version a person runs against real data.
Before you start

The fixture this plan assumes

Most failures in testing this slice come from a fixture that doesn't match the story, not from the code. Set these up first and the rest reads cleanly.

FIX-1People and a project

Do this

  1. Pick a project — call it AMPTJ — and set its Reporting Manager to Hari in Admin → Projects.
  2. Give it a start and end date, and a budget in hours.
  3. Make sure Hari, and two people in a different department (Meera, Rahul), all have logins linked to employee records.

Expect

Nothing yet — this is setup. If Hari has no linked profile, every later test fails silently rather than loudly, which is the single most common false result here.

FIX-2Hours that predate the test

Do this

Have Meera and Rahul each book time to AMPTJ, and have Meera also book time to a different project Hari has nothing to do with.

Expect

Meera's other-project hours are the control for the whole reporting section. Without them, the isolation tests pass for the wrong reason.

Migration 780

The role nobody types into

Project Manager is a system role, like Manager. Membership is derived from the project's Reporting Manager field and repaired by trigger, so a name never has to be maintained in two places.

ROLE-1Membership arrives from the project record

Do this

Open Admin → Security → Role Assignments and select Project Manager.

Expect

Hari is already a member. Nobody added him. The role is badged SYSTEM and carries a Sync button.

ROLE-2Handing the project over moves the role

Do this

Change AMPTJ's Reporting Manager from Hari to somebody else. Re-open Role Assignments.

Expect

The new manager is in the role; Hari is out — without pressing Sync. The trigger fires on the project update. Change it back before continuing.

ROLE-3Closing the project closes the role

Do this

Untick Active on AMPTJ. Check the role. Then tick it back.

Expect

Hari leaves the role while it is inactive and returns when it is active again. Renaming the project, or editing its budget, must not touch membership.

ROLE-4A hand-granted role survives the sync

Do this

Add somebody to Project Manager manually who manages no project. Press Sync.

Expect

They keep the role. The sync only ever removes grants it made itself, so an admin's deliberate exception is never quietly undone.

ROLE-5A leaver loses it

Do this

Set Hari's employment status to inactive, press Sync, then restore him.

Expect

Out while inactive, back on restore. Eligibility requires an active employee and an active project.

Migration 781

Project Members, resolved live

A target group that reads project_members on every request. No cache, no sync job — add somebody to a project and they are in the lead's scope on his next page load.

SCOPE-1The chip is reachable for the role that needs it

Do this

  1. Create a permission set — Project Lead.
  2. Tick Timesheet → View and the two Timesheet Report permissions.
  3. On Assignments, set Grant access to: Project Manager.

Expect

The target-group chips offered are Project members and Select target group →. If you instead see Direct L1 / Direct L2 / All levels, the frontend build has not deployed — the role would otherwise fall into the manager bucket on a substring match.

SCOPE-2Membership grants the person

Do this

Finish the assignment with Project Members and Include self ticked. Add Meera to AMPTJ on My Projects. Sign in as Hari and use RBP Troubleshooting on timesheet.view for Meera.

Expect

allowed for Meera. denied for somebody who is not on any of his projects.

SCOPE-3It is live, not cached

Do this

Remove Meera from the project. Re-run the same troubleshooting check. Do not press Sync anywhere.

Expect

Denied immediately. Re-add her and it is allowed again, same request. Nothing is scheduled or rebuilt in between.

Migration 782

The report shows the project, not the person's life

This is the section worth the most attention. A target group hands you an employee, and an employee carries all of their hours. The report has to hand you a project.

RPT-1The lead sees the project's full total

Do this

As Hari, open Admin → Reports → Timesheet Report → Project Summary.

Expect

AMPTJ's total includes Meera's and Rahul's hours even though they sit outside his normal access — his own hours alone would be wrong and he would have no way to know.

RPT-2…and nothing else

Do this

Switch to the Utilisation tab. Find Meera's row. Compare against the hours she booked to the other project in FIX-2. Export and check the file too.

Expect

Only her AMPTJ hours appear. Her other project is absent from the screen and the export. This is the case most likely to regress — she is inside his target population, so a report built from that alone would show everything.

RPT-3Current member vs outsider

Do this

On Utilisation, look at the Department column for a current member, then for somebody who booked to AMPTJ but is not a member.

Expect

Current member: department shown normally. Outsider: Hidden. The redaction now means you are seeing this line because it is your project, not because this is your person.

RPT-4Nobody else's report changed

Do this

Sign in as an HR user whose target group is All Employees. Run the same two tabs for the same period.

Expect

Output identical to before the release — no redaction, no missing rows, same totals. The project restriction applies only to people reached through Project Members.

RPT-5Both hats at once

Do this

Give a department head who also runs a project both assignments — one on Same department, one on Project Members.

Expect

Their own department in full, plus their project's outsiders clipped to that project. Losing their department members' non-project hours would be the regression to watch for.

Migrations 783 · 784 · 785 · 786

My Projects

Reached at /my-projects, gated on the Project team permission plus being the project's Reporting Manager. Two gates, not one — the permission says what you may do, the project record says where.

MP-1Only your own projects

Do this

As Hari, open My Projects. Then have somebody with the same permission but no projects open it.

Expect

Hari sees AMPTJ and no other project. The second person sees "No active project lists you as the Reporting Manager" — a named cause, not an empty screen.

MP-2The header carries real numbers

Do this

Read the card above the table.

Expect

Type chip, Runs, Team, Budget, Booked. With a budget set, a meter appears; past 100% it turns amber and says "over budget by N h" in words.

MP-3Hours rank the team

Do this

Look at the Team Allocation table. Click Name, then Hours.

Expect

Hours descending by default; the bar is scaled to the busiest member, not the project total. Sorting reorders current members and keeps past members separate.

MP-4Percentage saves and clears

Do this

Click Set in the Percentage column. Enter 50, press Enter. Re-open, clear it, save. Then try 0 and 101.

Expect

50% persists after a refresh; clearing returns it to Set. 0 and 101 are refused with "Allocation must be between 1 and 100 percent."

MP-5Start and end dates edit in place

Do this

Backdate a member's Start date. Set an End date in the future. Then clear the end date. Then try an end before the start.

Expect

All persist. Clearing returns the row to open-ended. End-before-start is refused in words before the request leaves the browser.

MP-6Removing decides for itself

Do this

Use the row action on somebody with no hours, then on somebody with hours.

Expect

The confirm appears inline — no browser dialog — and names the outcome: removed entirely for the first, end-dated today with their hours quoted for the second. After ending, the person appears under Show past members with their hours intact.

MP-7A closed project leaves the screen

Do this

Untick Active on AMPTJ and reload My Projects.

Expect

It disappears, matching the role and the scope — one rule everywhere. An administrator holding projects_mgmt.edit can still correct its membership; the lead's door is the one that closes.

Migrations 786 · 787

The timesheet offers the right projects

Two windows govern whether a project may be chosen for a date — the project's own dates, and the person's allocation. Both are now applied per day, and the list is resolved for the period being recorded rather than for today.

TS-1The list narrows to your projects

Do this

As Meera, open My Timesheet and start an entry.

Expect

The project dropdown offers the projects she is on, plus any she has booked to before — not every active project in the company.

TS-2Nobody is locked out

Do this

Sign in as somebody with no project membership and no booking history at all.

Expect

Every active project is offered — exactly the old behaviour. Project is a mandatory field, so narrowing must never be the reason a new joiner cannot record their first week.

TS-3The month you are filling in, not today

Do this

End a member's allocation in a past month — say it ran to 31 March. Now open March's timesheet for that person.

Expect

The project is offered for March. Open June and it is not. Before this the dropdown asked "are they a member now", so an old timesheet could be missing the project it needed.

TS-4Mid-month is a real boundary

Do this

Set an allocation ending on the 15th of the current month, on a project running to the end of the month. Try to add an entry on the 10th, then on the 20th.

Expect

10th project offered. 20th project not offered, and the panel says why: Not available for 20 Aug 2026: AMPTJ — outside the project's dates or your allocation to it.

TS-5Existing entries stay editable

Do this

Find an entry that sits outside its project's current window — the FIX-2 hours will do once you shorten something. Open it for edit.

Expect

Its project is still selectable on that date. An entry that exists must always be able to name its own project; otherwise the data that needs fixing is the data you cannot touch.

TS-6Create modal takes the intersection

Do this

Open the multi-day Create modal and select a range that straddles the 15th from TS-4.

Expect

The project is withheld, because it must be valid on every selected day — and the hint names it and says "all N selected days" rather than leaving it to be guessed.

TS-7Copy Day obeys the same rule

Do this

Copy a day containing that project's hours. Enter paste mode and look at the calendar, then try to paste onto the 20th.

Expect

The 20th is not offered as a paste target. If forced, the refusal names the project: AMPTJ is not available on that day — outside the project dates or your allocation Paste previously skipped both windows entirely, and a pasted entry then legitimised that day for the picker too.

Migration 788

A date change cannot strand somebody's hours

The refusal is the feature. It names how many entries, how many hours, which dates, whose, and the two ways out — so the person making the change can act on it without asking anyone.

GRD-1Shortening a project past booked hours

Do this

In Admin → Projects, move AMPTJ's end date earlier than the last day anybody booked to it. Save.

Expect

refused and nothing saved. The message reads roughly:

Cannot change the dates of AMPTJ: 2 timesheet entries (15.00 h) fall outside it — between 2026-08-18 and 2026-08-20, by Meera R. Move the date to cover them, or remove those entries first.
GRD-2Shortening to a date that still covers them

Do this

Move the end date to exactly the last booked day, then to one day after.

Expect

saved both times. The rule is about stranding hours, not about shortening.

GRD-3The same rule on an allocation

Do this

On My Projects, set a member's End date earlier than their own last booked day on that project.

Expect

Refused, as a readable sentence in the page's error banner — not a raw database error. Only their entries count: another member's later hours must not block it.

GRD-4Bad data can still be corrected

Do this

Find a project already in the stranded state — entries after its end date, created before this release. Move its end date later, to cover them.

Expect

saved. The guard blocks only what this edit newly strands. A blanket rule would have refused every edit to that project, including the one that fixes it.

GRD-5Nothing is deleted, ever

Do this

After any refusal, check the affected timesheets and re-run last month's Project Summary.

Expect

Every entry still there, approved sheets still valid, totals unmoved. The guard refuses the edit; it never resolves the conflict by removing work somebody actually did.

GRD-6Unrelated edits are untouched

Do this

On a project in the stranded state, change its name, type or budget.

Expect

Saves normally. The guard watches the date columns only.

Known and deliberate

Not defects

Three behaviours will look like bugs to a tester who does not know they were chosen. Record them as observations, not failures.

What you'll seeWhy it is that way
The dropdown is only an offer — a direct API call can still write an entry against any active project. No enforcement trigger has been added. It is the one change that can stop somebody recording their week, so it waits until a read-only audit shows how much existing data it would refuse.
A project you have booked to before stays offered on dates within its own window, even after your allocation ends. Deliberate. An entry that exists must be able to name its own project, or old timesheets become uneditable. Closing it needs enforcement with an exemption for existing rows.
An allocation can run past the end of the project it is on, and nothing warns you. Data hygiene rather than behaviour — the project window binds anyway, so the surplus allocation grants nothing. A warning on My Projects is a candidate follow-up.
